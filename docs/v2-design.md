# 方块搭子 V2 设计方案

> 状态：Design baseline / 开发基准
>
> 目标：在不破坏 V1 已有成员数据和使用习惯的前提下，把“离散标签问卷”升级为更精细、更可解释、更低负担的渐进式玩家画像与匹配系统。

## 1. V2 要解决的问题

V1 已经验证了产品核心链路：成员填写资料 → 回答若干 Minecraft 偏好问题 → 实时看到 Top 3 搭子 → 可复制公开 QQ。

内测后暴露出两个主要问题：

1. **画像信息损失较大**：例如“兴趣最多选 3 项”“角色最多选 2 项”，无法区分“没选是因为不喜欢”还是“只是没挤进前三”。
2. **不同类型的数据使用了相似的单选/多选交互**：兴趣强度、上线时间、合作习惯、角色意愿本质不同，不应全部压缩成离散标签。

V2 的目标不是让问卷更长，而是让每一次交互产生更多有效信息，并继续保持“边回答、边看到匹配变化”的体验。

## 2. 产品原则

### 2.1 渐进式画像，而不是一次性考试

用户不需要完成全部问卷才能获得结果。

首轮只采集三个高价值模块：

1. 玩法兴趣与近期意图
2. 一周可上线时间
3. 核心多人游戏习惯

完成这三屏后即可获得正式 Top 3。角色、边界、存档周期、教学/研究习惯等信息作为后续“让推荐更准”的渐进式问题。

### 2.2 `null` 与 `0` 永远不同

- `null`：用户尚未表达，不参与匹配，也不扣分。
- `0`：用户明确表达“不喜欢 / 基本不会 / 不愿意”，可以产生真实负向信息。

V1 的未选项不能迁移成 V2 的 `0`。

### 2.3 偏好、容忍度、硬约束分开

同一个人可能“更喜欢 A，但 B 也能接受”。因此 V2 不只记录理想值，还允许记录容忍度。

统一模型：

```ts
{
  ideal: 0 | 1 | 2 | 3 | 4,
  tolerance: 0 | 1 | 2
}
```

只有用户主动标记“这是我的硬性要求”时，系统才允许把该条件升级为 hard constraint。算法不得自行推断硬约束。

### 2.4 相似性与互补性分开

- 兴趣、上线时间、推进节奏等主要看**相似性 / 可共存性**。
- 队伍角色、教学关系等主要看**互补性**。

不能用“两个字段越相同越好”的单一规则处理所有维度。

### 2.5 解释性优先

每一次匹配必须能够回答“为什么推荐 TA”。匹配引擎除分数外，同时输出 `confidence` 和 `reasons`。

## 3. 首轮 V2 用户旅程

### 3.1 身份资料

继续沿用 V1：

- 社团昵称 / MC ID
- QQ（5–12 位数字）
- 自我介绍（可选，最多 120 字）
- 是否愿意在匹配结果中公开 QQ
- 可选邮箱绑定/恢复

### 3.2 第一屏：玩法兴趣 + 近期意图

标题：**最近什么最容易把你叫上线？**

玩法类别：

- 科技整合包
- 原版 / 类原版生存
- 建筑 / 景观
- 红石 / 原版自动化
- 魔法模组
- 冒险 / RPG
- 高难 / 专家包
- 小游戏 / 派对玩法
- PVP / 对抗
- Mod / 服务端 / 技术开发

“社交 / 在服里一起待着”不再作为玩法兴趣，后续独立建模。

每项为 5 档语义评分：

- 0：不想玩
- 1：有人叫可以
- 2：偶尔想玩
- 3：挺想玩
- 4：最近很想玩
- 未操作：`null`

用户无需评价全部项目；至少评价 2 项且至少 1 项大于 0，即可继续。

另外允许最多标记 2 项 **🔥 最近正想找人玩这个**，作为 `currentIntents`。近期意图权重高于长期兴趣，并带更新时间。

### 3.3 第二屏：一周上线时间热力图

标题：**什么时候最容易在服务器碰到你？**

采用 7 天 × 3 时间段：

- 下午
- 晚上
- 深夜

每格：

- 未设置：未知
- 1：偶尔
- 2：经常

提供快速填写：

- 基本每天晚上
- 工作日晚
- 周末比较多
- 时间很随机

并单独记录 `availabilityRandomness`，不把“随机”混入具体时间段。

匹配关注的是“是否存在真实共同上线窗口”，不是两个人课表长得是否相似。

### 3.4 第三屏：核心多人游戏习惯

标题：**一起开档时，你通常怎么玩？**

首轮只采集三个高价值轴，每个使用 5 档语义选择：

1. **推进强度**：更看重体验 ↔ 更看重推进
2. **行动同步**：喜欢一起行动 ↔ 喜欢各自发展
3. **分工程度**：大家一起做 ↔ 喜欢明确分工

每项允许额外选择“其实两边我都能适应”，后台映射为更高 tolerance，而不是简单等同于中间值。

### 3.5 首轮正式推荐

第三屏完成后进入正式 Top 3：

- 匹配度 Compatibility
- 了解程度 Confidence
- 2–3 条匹配理由
- 自我介绍
- 公开 QQ 的复制按钮

前三屏之前右侧仍可实时出现“初步推荐”，但不展示过度精确的百分比。

## 4. 后续渐进式模块

这些模块不阻塞首次匹配。

### 4.1 队伍角色意愿

角色：

- 路线规划 / 查资料
- 机器 / 红石 / 技术
- 建筑 / 基地
- 资源收集
- 探索 / 跑图
- 战斗 / Boss
- 仓储 / 后勤
- 组织公共项目

值：

- 0：不太想负责
- 1：可以负责
- 2：很愿意负责
- `null`：未知

角色算法主要奖励互补，不把角色不同当作天然不匹配。

### 4.2 舒适区与边界

包括：

- 语音接受度
- 资源共享程度
- 队伍规模
- 存档周期
- 约局计划性
- 异步推进接受度

使用 `ideal + tolerance`。用户可主动标记某项为 hard constraint。

### 4.3 教学与研究

低权重模块：

- 愿意带人 `teach`
- 希望被带 `learn`
- 查资料独立程度 `researchIndependence`

其中教学关系按互补性计算。

### 4.4 Adaptive Questions

首轮完成后不再显示“第 4/12 题”。改为：

> 让推荐再准一点

下一题由匹配引擎选择。优先级大致为：

`维度权重 × 当前 Top 候选人的差异度 × 当前缺失程度`

即优先询问最可能改变当前 Top 3 排名的问题。

## 5. 匹配算法 V2

### 5.1 三个核心输出

- `compatibility`：两个人一起玩的适配程度（0–100）
- `confidence`：当前共同已知信息的覆盖程度（0–1）
- `rankingScore`：内部排序值；低置信度的虚高匹配会向中性值收缩

推荐排序不直接按 compatibility。

### 5.2 基础模块权重

初始建议：

| 模块 | 权重 |
|---|---:|
| 最近想玩什么 | 25% |
| 长期玩法兴趣 | 18% |
| 上线时间 | 22% |
| 多人游戏习惯 | 15% |
| 队伍角色互补 | 10% |
| 舒适区 / 边界 | 7% |
| 教学、研究等细节 | 3% |

首轮未采集的模块不参与 compatibility，并通过 confidence 体现信息不足。

### 5.3 近期意图

核心问题不是“双方 intent 标签完全一致吗”，而是：

> 我现在想玩的东西，你是否也愿意玩？

双方分别计算 readiness 后合并。双方近期意图相同为强加分；一方近期想玩、另一方对此长期兴趣较高也可获得较高分。

近期意图随时间衰减：

- 0–14 天：100%
- 15–30 天：逐渐衰减
- 30 天后：不再按近期意图加权，并提示用户更新

### 5.4 长期兴趣

直接共同兴趣以较低一方的兴趣强度为主要基础，即更接近 `min(A, B)`，并保留少量“相关兴趣 affinity”补充。

相关兴趣只能小幅加分，不能替代直接共同兴趣。

### 5.5 上线时间

时间匹配重点是：

1. 较忙的一方主要可用时间有多少被另一方覆盖
2. 双方是否拥有多个稳定共同窗口

不让“几乎任何时间都有空”的用户天然获得异常高的时间分。

### 5.6 游戏习惯

对 `ideal + tolerance` 计算有效差异。理想值不同但至少一方非常灵活时，不应被判为强冲突。

### 5.7 角色与教学

角色：互补为主、共同兴趣为辅。

教学：`A.teach ↔ B.learn` 和 `B.teach ↔ A.learn` 交叉计算。

### 5.8 Hard Constraints

只有双方明确存在不可共存的硬约束时才直接 `eligible = false`。普通偏好冲突只扣分。

### 5.9 Confidence 与排名收缩

未知信息不计 0 分，只降低 confidence。

推荐排序使用置信度收缩：高 compatibility + 极低 confidence 的候选人，不应排在信息充分且稳定匹配的人前面。

### 5.10 推荐理由

每个 scoring module 同时产出理由候选，例如：

- 最近都很想玩科技整合包
- 周五晚、周六晚经常同时在线
- 都偏好明确分工
- TA 偏建筑与资源，你偏技术与规划

最终取价值最高的 2–3 条展示。

## 6. V2 数据模型

### 6.1 表拆分

继续保留：

- `member_profiles`：昵称、自我介绍、V1 兼容资料、discoverable
- `member_contacts`：QQ 与 show_qq

新增：

- `member_match_profiles`：完整 V2 匹配画像
- `match_feedback`：后续反馈/行为数据

### 6.2 `member_match_profiles`

建议字段：

```text
user_id
profile_version
interest_scores          jsonb
current_intents          text[]
intent_updated_at        timestamptz
availability_grid        jsonb
availability_randomness  smallint
playstyle_preferences    jsonb
role_preferences         jsonb
boundary_preferences     jsonb
learning_preferences     jsonb
created_at
updated_at
```

完整画像只允许本人直接读取/写入；其他成员不应直接获得精细上线规律或边界数据。

### 6.3 `match_feedback`

预留：

- 推荐对象
- 👍 / 😐 / 👎
- 负反馈原因
- 是否复制 QQ
- 时间戳

V2 初期只记录，不自动训练模型，避免小样本过拟合。

## 7. 服务端匹配与隐私

V1 在浏览器下载其他成员画像后本地计算。V2 由于会采集精细时间热力图和边界信息，改为服务端匹配。

静态站点继续保留，匹配逻辑部署到 Supabase Edge Function：

```text
浏览器
  → 保存自己的 V2 画像
  → 调用 match-v2
  → Edge Function 读取候选数据并计算
  → 只返回候选人的展示资料、score、confidence、reasons、可公开 QQ
```

不向客户端返回候选人的完整 V2 向量、完整时间表或边界配置。

匿名登录用户同样通过 Supabase JWT 调用 Edge Function。

## 8. V1 → V2 兼容与迁移

不删除 V1 字段，不要求所有旧用户立即重填。

### 8.1 可以安全预填的内容

- V1 已选兴趣 → V2 可预填为中等偏高兴趣，但必须让用户确认
- V1 已选角色 → V2 可预填为“可以负责”，不能默认成“很愿意”
- 部分单选字段可作为 UI 建议值

### 8.2 不允许推断的内容

- V1 没选某兴趣 ≠ V2 的 0
- V1 `weekday_evening` 不能展开成周一至周五全部经常在线
- V1 的 `flexible / adaptive` 不强行映射成精确 tolerance

### 8.3 跨版本匹配

V2 用户仍可匹配 V1 用户。匹配引擎对 V2 数据做保守聚合，与 V1 粗粒度字段比较，并降低这部分 confidence。

V1 用户不会因为 V2 上线而从匹配池消失。

## 9. 视觉与交互定稿

首页继续维持现有偏深、电影感的 Minecraft 场景。

进入答题后：

- 保留同一个 Minecraft 背景
- 提高背景亮度与通透感
- 减弱暗色遮罩
- 使用浅白/浅绿色磨砂玻璃卡片
- 文字改为深墨绿 / 深灰
- 继续使用现有绿色强调色

整体感觉应是“从首页的沉浸式场景走进更明亮的社交空间”，而不是切换成另一个网站。

桌面端继续保持左侧问题、右侧 Top 3；手机端问题在上、推荐在下，默认重点展开 Top 1。

## 10. V2 第一阶段开发范围

第一阶段必须真正可上线，包含：

1. `member_match_profiles` 数据表与 RLS
2. `match-v2` Edge Function
3. V1/V2 兼容匹配
4. 第一屏：兴趣强度 + 近期意图
5. 第二屏：7×3 上线时间热力图 + 快速填写
6. 第三屏：三个核心游戏习惯轴
7. Compatibility / Confidence / Reasons
8. Top 3 实时重排
9. 更明亮但与首页一致的答题视觉
10. V1 老用户保留并可继续参与匹配

角色、硬边界、反馈学习、自适应追问在数据结构和算法中预留接口，可在后续小版本继续接入，不阻塞第一阶段上线。

## 11. 验收标准

- 老用户数据不丢失，V1 用户仍可被匹配
- 新用户前三屏即可得到正式 Top 3
- 未回答与明确 0 在匹配中严格区分
- 候选人的精细 V2 画像不会直接暴露给其他浏览器客户端
- 推荐卡能稳定显示匹配度、了解程度和可解释原因
- 移动端可完成全部首轮流程
- 静态导出 `out/` 继续可用于 NAS/Nginx/FRP 部署
- CI `npm run build` 通过
