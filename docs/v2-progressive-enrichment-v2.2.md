# 方块搭子 V2.2：渐进式补充画像

## 状态

V2 三个核心模块完成后立即产生正式 Top 3；后续信息不再作为阻塞式长问卷，而以“让推荐再准一点”的方式逐块补充。

## 五个补充模块

1. **队伍与存档**
   - 理想队伍规模：2 人 / 3–5 人 / 6–10 人 / 11–20 人 / 大社区
   - 理想存档周期：一次活动 / 1–2 周 / 1–2 个月 / 3–6 个月 / 半年以上
   - 队伍规模与存档周期均可由用户主动标记为硬性要求。

2. **沟通与约局**
   - 语音习惯：完全不语音 ↔ 基本开麦
   - 约局计划性：临时喊人 ↔ 提前约好
   - 异步推进接受度：希望同时在线 ↔ 很接受异步推进
   - 语音可以主动标记为硬性要求。

3. **资源习惯**
   - 各自独立 ↔ 全部共享
   - 中间档“核心共享”代表公共核心资源共享，同时允许一定个人边界。

4. **队伍角色**
   - 路线规划 / 查资料
   - 机器 / 红石 / 技术
   - 建筑 / 基地
   - 资源收集
   - 探索 / 跑图
   - 战斗 / Boss
   - 仓储 / 后勤
   - 组织公共项目
   - 每项：不太想负责 / 可以负责 / 很愿意负责
   - 不要求全部填写；评价 4 项即可完成模块。这样仍然保持低负担，同时给角色互补算法保留足够信息。

5. **教学与研究**
   - 愿意带人
   - 希望被带
   - 查资料独立程度

## 渐进式交互

- 基础画像完成度与匹配 Confidence 分离。
- 三个核心模块完成后，基础画像固定为 100%。
- 补充画像单独显示 `0/5 ... 5/5`。
- 用户任何时候都可以“暂时到这里”，不会影响联系 Top 3。
- 每保存一个补充模块，立即重新调用服务端 `match-v2` 计算 Top 3、Compatibility、Confidence 和推荐理由。
- 不显示“第 4/12 题”等长问卷序号。

## Adaptive Module Suggestion

`match-v2` 会在每次匹配结果中返回：

- `nextModule`
- `nextModuleReason`

候选模块为：

- `team`
- `communication`
- `resource`
- `roles`
- `learning`

选择逻辑综合：

1. 当前用户是否缺失该模块；
2. 模块对匹配的重要程度；
3. 当前高排名候选人在该模块上的数据离散程度。

因此系统会优先追问更可能改变当前 Top 3 的模块，而不是固定顺序机械答题。

## 服务端评分更新

V2.2 正式启用：

- `boundary_preferences` 的 Compatibility/Confidence 计算；
- 角色互补评分；
- 教学关系的交叉互补评分；
- `sessionPlanning` 与 `resourceSharing` 的完整多人习惯覆盖；
- 显式 hard constraint 检查。

Hard constraint 只能由玩家主动设置。未设置 hard 的普通偏好冲突只降低分数，不直接淘汰候选人。

## V1 Bridge

为避免 V1 老成员在迁移期间突然失去信息价值，服务端会保守映射已有：

- duration
- group_size
- communication
- session_style
- resource_style
- research
- experience_style

这些桥接数据质量低于 V2 显式填写，因此 Confidence 保守计算。

## 行为反馈

匹配卡新增：

- 👍 合适
- 😐 一般
- 👎 不太合适
- QQ 复制行为

写入 `match_feedback`。当前阶段只收集，不自动训练或修改匹配权重，避免内测样本过少导致过拟合。

## 隐私

完整 `member_match_profiles` 仍只有本人可通过普通客户端直接读取。其他成员的精细时间表、边界、角色等信息只在 Edge Function 服务端参与计算，客户端只收到匹配卡所需的分数、Confidence、推荐理由和公开联系方式。
